# 3x-ui Server Setup 2.8 — очищенный проект

Установщик для **чистого Ubuntu 22.04/24.04 VPS**: официальная панель 3x-ui, SSH на `1335`, новый администратор, UFW, Fail2ban, HTTPS по домену или публичному IP, Nginx, сайт-заглушка «Тихие маршруты», страница 404 и отдельный WireGuard (`51820/UDP`, профили «Роутер» и «Роутер (Катя)»).

**База в установщик не вшита.** Сначала устанавливается пустая панель, затем базу можно восстановить через веб-интерфейс. Приватные базы и ключи не помещайте в публичный GitHub.

## Запуск с GitHub

Скопируйте **все файлы и каталоги** из архива в корень `evgeny-dmitrievich/3x-ui-server-setup` (`main`). Затем на чистом VPS:

```bash
curl -fsSL https://raw.githubusercontent.com/evgeny-dmitrievich/3x-ui-server-setup/main/setup.sh -o /tmp/3x-ui-setup.sh && sudo bash /tmp/3x-ui-setup.sh
```

Это системная установка: она меняет SSH и firewall. Используйте только тестовый VPS с резервной копией/snapshot и консолью провайдера. **На действующем сервере `setup.sh` запускать не следует.**

## Обновление инструментов на уже установленном VPS

После публикации новой версии в GitHub достаточно один раз обновить помощники, **без переустановки 3x-ui**:

```bash
curl -fsSL https://raw.githubusercontent.com/evgeny-dmitrievich/3x-ui-server-setup/main/update-import-tools.sh -o /tmp/3x-ui-update-import.sh && sudo bash /tmp/3x-ui-update-import.sh
```

Это обновляет только три служебных файла и создаёт их резервные копии. **`3x-ui-after-import` автоматически не запускается.** Текущая база и nginx остаются прежними до осознанного запуска операции.

## Восстановление базы

Если резервная база с другого сервера содержит старые пути сертификатов, она может не пройти восстановление через 3x-ui. Для такого случая есть отдельный безопасный подготовительный шаг:

```bash
sudo 3x-ui-prepare-import /home/evgen/source.db
```

Эта команда создаёт рядом новый `.db`, исправляя SSL-пути и адреса подписок. Оригинал и работающая база не меняются. В случае отдельной проблемы TUIC допускается ручной вариант `--disable-tuic`: он временно выключает TUIC в подготовленной копии, **не удаляя конфигурацию или клиентов**. Он не применяется автоматически и не зависит от версии панели.

После успешного восстановления подготовленной базы в веб-интерфейсе:

```bash
sudo 3x-ui-after-import
```

**Что делает `3x-ui-after-import`:**

- Читает реальные записи `inbounds` и параметры панели непосредственно из активного SQLite-файла. Нет обязательных имен, ID, портов и количества подключений — 3, 10, 15 и другие числа допустимы.
- Восстанавливает/обновляет адреса публичного сервера и TLS-пути в отдельной копии SQLite. **Не меняет** названия, клиентские UUID, пароли, REALITY-ключи, SNI, target и клиентскую статистику.
- Генерирует маршруты `Nginx stream` для имеющихся TCP REALITY/MTProto-подключений по их SNI, при необходимости добавляет промежуточные локальные порты для PROXY protocol.
- Генерирует HTTP-маршруты WebSocket/gRPC/XHTTP там, где они возможны, подключает панель и подписки по фактическим портам и путям, сохраняет заглушку и страницу 404.
- При конфликте SNI или HTTP-пути **не угадывает**, какой backend использовать: пропускает конфликтный маршрут с предупреждением. Неподдерживаемые для такого Nginx-сценария подключения остаются в базе и сохраняют свои параметры.
- Для поддерживаемых активных UDP-входов открывает соответствующие UDP-порты UFW после успешной проверки панели; произвольные TCP-порты автоматически в интернет не открываются.
- Делает SQLite-backup (включая WAL), проверяет синтаксис Nginx, запускает службу и проверяет HTTP-ответ панели, заглушки и страницы 404. При неудаче возвращает прежнюю базу и конфигурацию.
- Повторный вызов **разрешён**, например после очередного восстановления базы, и повторно согласует маршруты.

Это **не** патчер конкретной версии панели. Никакого требования использовать именно 3.10.2 или 3.11.0 нет. Однако новые схемы таблиц или протоколы, отсутствующие в генераторе, не могут гарантированно работать без адаптации. Сценарий не изменяет версию 3x-ui и не автоматически выключает TUIC. Для неизвестных маршрутов выводится диагностическое предупреждение.

### Смена домена / возврат на IP

```bash
sudo 3x-ui-change-domain
```

Смена публичного адреса не переименовывает существующие подключения и не меняет SNI REALITY. Сторонние адреса в «Хостах», не совпадающие с адресом этого сервера, сохраняются. Если нужна смена **самого** SNI REALITY, это отдельная операция в панели и настройках клиентов.

### Проверка после применения

```bash
sudo nginx -t
sudo systemctl status x-ui nginx fail2ban --no-pager
sudo ss -lntup | grep -E ':(1335|443|51820)\b'
```

Ссылки подписок необходимо обновить в клиентских приложениях при смене адреса. Наличие настроенного inbound в базе не гарантирует, что конкретный протокол поддерживается установленной версией Xray или клиентом VPN.

## WireGuard

```bash
sudo 3x-ui-wg status
sudo 3x-ui-wg export all
sudo 3x-ui-wg add 'Дополнительный роутер'
```

Файлы профилей содержат приватные ключи. Не публикуйте их на GitHub или на сайте-заглушке.

## Локальные тесты проекта

```bash
python3 tests/test_dynamic_inbounds.py
python3 tests/test_release_integrity.py
python3 tests/test_bootstrap.py
python3 tests/test_healthcheck_mock.py
python3 tests/test_pre_import.py
```

Тесты сами создают локальную **искусственную** SQLite-базу без реальных пользователей или ключей (`tests/make_fixture.py`). Они не заменяют реальное развёртывание и проверку каждого VPN-протокола на новом VPS.

## Структура репозитория

- `setup.sh` — установка на чистом сервере одной командой.
- `stack-manager.sh`, `db_tool.py` — логика настройки Nginx и базы после импорта.
- `configure-after-import.sh`, `change-domain.sh` — короткие обязательные точки входа для команд на сервере.
- `prepare-import.sh` — предварительная подготовка внешней SQLite-базы (при необходимости).
- `update-import-tools.sh` — безопасное обновление служебных инструментов на существующем сервере.
- `landing/` — страницы сайта (включая 404) и скрипт первичной настройки HTTPS.
- `wireguard/` — установка и управление профилями WireGuard.
- `tests/` — регрессионные тесты и синтетический тестовый набор данных.

**Удалены старые разовые помощники** `resume-after-fail2ban.sh` и `reality-443.sh`, а также дублирующий тест `test_db_tool.py`. Для восстановления после сбоев на новом сервере используйте снапшот провайдера и диагностику, а не повторный запуск `setup.sh` на работающей машине.

При обновлении GitHub загрузка нового архива **не удаляет** ранее опубликованные файлы. Удалите устаревшие файлы в GitHub отдельно через интерфейс или `git rm`.
